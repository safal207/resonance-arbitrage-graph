# v0.16 — Predictive Opportunity Layer

v0.16 begins the transition from deterministic opportunity verification to leakage-safe predictive research while keeping the repository paper-only.

The goal is **not** to predict raw crypto prices in isolation. The useful target is whether an already-identified route is likely to remain economically useful after the market evolves.

## Causal spine

```text
captured replay market state
→ one collapsed logical operation
→ decision-time feature row
→ later outcome becomes target
→ outcome-availability-safe chronological split
→ model fit on past-only evidence
→ untouched shadow validation
→ calibration + paper-PnL diagnostics
→ candidate strategy evidence
→ existing promotion / lineage / authority layers
```

The predictive layer is advisory. It does not bypass the deterministic verifier, regime gate, holdout validation, policy promotion, lineage registry, or authority controls.

## Initial prediction targets

Each predictive row separates decision-time inputs from labels that only become available later.

Targets are:

- `realized_net_edge_bps` — later realized paper net edge when observed;
- `survived` — whether the opportunity produced a realized outcome instead of expiring;
- `positive_edge` — whether the realized paper edge was strictly positive;
- `met_required_edge` — whether the realized paper edge cleared the deterministic policy threshold active for that case.

An incomplete replay outcome carries no training labels.

## Decision-time feature contract

The first feature set deliberately reuses fields already derived from evidence-bound market state:

```text
expected_edge_bps
required_edge_bps
route_hops
total_cost_bps
total_latency_ms
min_success_probability
normalized_spread_bps
top_of_book_capacity_ratio
quote_age_ms
quote_age_dispersion_ms
cross_rate_dislocation_bps
short_window_return_volatility_bps
market_regime
```

The row also binds:

- `case_id`;
- `logical_operation_id`;
- semantic `route_id`;
- decision timestamp;
- start amount;
- source replay-case SHA-256.

The dataset collapses retries before feature extraction, preserving one row per logical operation.

## Leakage firewall

Ordinary chronological splitting is not enough.

Consider:

```text
operation A decision: 10:00
operation B decision: 10:05
operation C validation decision: 10:10
operation B outcome arrives: 10:20
```

Even though B's *decision* is earlier than C, B's target was not known at 10:10. Training on B would leak future information into C.

Therefore v0.16 uses two clocks:

```text
decision_at_ms
target_available_at_ms
```

A row enters training only when:

```text
decision_at_ms < validation_start_ms
AND target_available_at_ms <= validation_start_ms
```

Earlier decisions whose targets arrive late are explicitly reported as excluded rather than silently included or dropped.

## Baseline before ML frameworks

v0.16 intentionally starts with a dependency-free `HistoricalMeanBaseline`.

It predicts:

- mean realized edge from leakage-safe training rows;
- empirical survival probability;
- empirical positive-edge probability.

This baseline is intentionally weak. Its job is to establish a deterministic benchmark that CatBoost, LightGBM, XGBoost, PyTorch or future sequence models must beat out-of-sample.

Adding a large model before a trustworthy benchmark would make it harder to distinguish actual signal from leakage or overfitting.

## Shadow evaluation

The first shadow report includes:

- mean absolute realized-edge error;
- survival Brier score;
- positive-edge Brier score;
- number of rows selected by explicit caller-supplied probability thresholds;
- selected rows with realized outcomes;
- selected expired rows;
- `selected_realized_pnl_units`.

`selected_realized_pnl_units` is computed only from replay outcomes that actually contain a realized edge:

```text
start_amount × realized_net_edge_bps / 10_000
```

Expired selections are counted separately rather than assigned invented losses. This prevents the first predictive layer from pretending to know execution costs or fill losses that were not present in the replay evidence.

## Why RL comes later

Reinforcement learning changes a harder object than supervised forecasting: it learns an action policy whose own choices affect the future data distribution.

Before offline RL is introduced, the system should first prove that:

1. predictive features contain stable out-of-sample signal;
2. target availability is leakage-safe;
3. calibration remains stable across time/regime/route slices;
4. model-selected opportunities improve paper outcomes versus deterministic and naive baselines;
5. candidate-model identity and training evidence can be bound into the existing policy promotion chain.

The intended next sequence is:

```text
v0.16 predictive dataset + supervised shadow models
→ model artifact/evidence binding
→ walk-forward model comparison
→ offline policy learning / contextual bandit baseline
→ offline RL candidate
→ promotion firewall
```

## External model adapters

Future model adapters should consume the deterministic v0.16 row contract rather than reaching directly into live exchange objects.

Likely order:

1. CatBoost / LightGBM tabular baseline;
2. calibrated ensemble;
3. sequence model over rolling windows;
4. PyTorch time-series model;
5. offline contextual-bandit / RL policy.

The repository should keep these optional so the verification core remains lightweight.

## Trust boundary

v0.16 does not:

- place live orders;
- connect private exchange APIs;
- sign wallet transactions;
- move stablecoins;
- automatically activate learned models;
- treat backtest PnL as live profitability;
- hide model thresholds as trading recommendations.

A predictive or learned policy remains a candidate. Existing validation, promotion, lineage and authority mechanisms remain the governance path for any future policy transition.
