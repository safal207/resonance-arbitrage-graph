# v0.15 — Evidence-Bound Policy Authority & Delegation

v0.15 adds an explicit governance authority layer above the v0.14 policy lineage registry.

## Causal spine

```text
authority basis + evidence
→ root authority grant
→ scoped delegation
→ effective grant check
→ RELEASE / SUPERSEDE / REVOKE authorization
→ exact v0.14 registry event SHA
→ authorization receipt
→ complete authority-governed registry receipt
```

The purpose is not to decide whether a policy is economically good. v0.13 already owns promotion evidence, and v0.14 owns canonical policy lineage. v0.15 answers a different question:

> Who was permitted to perform this governance transition, under what authority basis, with what scope, and against which exact evidence-bound event?

## Trust boundary

`authority_id` is an explicit governance identifier, not a cryptographic proof of a real-world identity.

v0.15 proves:

- the authority identifier was admitted through a deterministic grant;
- the grant has a non-empty `authority_basis` and evidence SHA-256;
- delegation derives from an existing effective parent grant;
- delegated actions are a subset of the parent's actions;
- policy context scope is exact and cannot silently broaden;
- the complete parent-grant chain is bound into each authorization receipt;
- the grant and all ancestors were effective in the authority-ledger snapshot bound by the receipt;
- the requested action matches the exact v0.14 registry event type;
- the authorization receipt binds the exact registry event SHA-256.

v0.15 does **not** claim that an authority identifier is authenticated by a private key, certificate, DID, hardware root, employee directory, or other external identity system. Such authentication can be layered on later without changing the causal governance model.

## Actions

The base authority vocabulary is intentionally small:

- `RELEASE` → v0.14 `RELEASED`
- `SUPERSEDE` → v0.14 `SUPERSEDED`
- `REVOKE` → v0.14 `REVOKED`

An authorization action must map exactly to its registry event type.

## Authority grants

A grant identity is deterministic over:

```text
authority_id
authority_basis
policy_context_sha256
actions
parent_grant_id
evidence_sha256
```

and receives a `pag_<sha256>` grant ID.

A root grant has no parent. Every delegated grant names exactly one parent grant.

### Monotonic delegation

Delegation may only reduce authority.

For a child grant:

```text
child.actions ⊆ parent.actions
child.policy_context_sha256 == parent.policy_context_sha256
```

The current v0.15 scope model deliberately uses exact `policy_context_sha256` equality instead of wildcards or hierarchical scopes. This prevents accidental cross-context authority expansion.

Self-delegation and repeated ancestor authority identities are rejected. Since a child may only reference an already-existing parent grant in the append-only ledger, forward grant cycles are structurally impossible; verification still checks the chain defensively.

## Authority ledger

Authority history is append-only and hash-chained:

```text
ROOT_GRANTED
→ DELEGATED
→ DELEGATED
→ GRANT_REVOKED
```

Each event binds `previous_event_sha256`.

Ledger snapshots expose:

- all grants;
- direct revoked grants;
- effective grants;
- the deterministic root grant;
- the full event chain.

Tampering with an old event without reproducing every subsequent link breaks verification.

## Revocation semantics

Grant revocation is **forward-only**.

If a parent grant is revoked, that grant and all descendants become ineffective in the new ledger snapshot. They cannot authorize future policy registry events.

Historical authorization receipts remain valid when verified against the exact older authority-ledger snapshot that they originally bound. Revocation therefore stops future authority without rewriting causal history.

This distinction is deliberate:

```text
valid at event time ≠ valid forever for new actions
```

## Authorization receipt

An event authorization receipt binds:

- authority ledger SHA-256;
- leaf grant ID;
- complete root → leaf grant chain;
- `authority_id`;
- action;
- exact policy context SHA-256;
- v0.14 registry event sequence;
- v0.14 registry event SHA-256;
- v0.14 registry event type;
- authorization evidence SHA-256.

The receipt is canonical JSON with its own SHA-256 envelope.

`verify_policy_authorization_binding()` reconstructs the receipt from the authority ledger snapshot and v0.14 registry event rather than merely checking the outer digest.

## Complete registry authority receipt

A `PolicyAuthorityRegistryReceipt` binds the final v0.14 registry SHA-256 plus exactly one authorization receipt per registry event.

`verify_policy_authority_registry_full_binding()` requires complete event coverage and re-verifies every authorization against its own bound authority-ledger snapshot.

This allows different events in the same policy lineage to be authorized under different historical authority snapshots while preserving exact causal evidence.

## CLI

The offline CLI is exposed as:

```text
resonance-policy-authority
```

Commands:

```text
bootstrap
delegate
revoke-grant
authorize
verify-ledger
verify-authorization
registry-receipt
verify-registry-receipt
```

The CLI only reads/writes deterministic JSON receipts. It has no exchange credentials, signing keys, network execution, orders, transfers, bridges, or live trading path.

## Safety boundary

`ACTIVE` policy in v0.14 and authorized governance in v0.15 remain paper-policy concepts. They do not deploy code or activate real trading.

v0.15 is governance evidence infrastructure, not a live execution control plane.
