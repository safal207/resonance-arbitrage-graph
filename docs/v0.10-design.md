# v0.10 — Joint Causal Holdout Calibration

## Goal

v0.10 jointly calibrates two decision thresholds that are now causally active:

- verifier `execute_net_edge_bps`;
- regime `volatile_return_bps`.

The volatility threshold became causally active only after v0.9 introduced the regime execution gate. Before v0.9, changing `NORMAL` to `VOLATILE` changed a label but did not necessarily change the final paper verdict.

## Causal spine

```text
captured replay corpus
  -> logical-operation groups
  -> strict chronological split
  -> calibration-only 2D candidate grid
  -> 2x2 counterfactual replay
  -> recompute base verifier verdict
  -> recompute market regime
  -> recompute v0.9 regime gate
  -> final verdict
  -> causal-support accounting
  -> select calibration winner
  -> freeze candidate pair
  -> untouched validation
  -> out-of-sample report
```

## 2×2 counterfactual support

A threshold value is not considered useful just because the regime label changes. Each candidate pair is evaluated on the same captured market bytes under four policy cells:

```text
baseline (00)
  = baseline execute + baseline volatility

execute-only (10)
  = candidate execute + baseline volatility

volatility-only (01)
  = baseline execute + candidate volatility

joint (11)
  = candidate execute + candidate volatility
```

The two tuned dimensions are then attributed symmetrically:

```text
execute support
  = final verdict(11) != final verdict(01)
  # candidate volatility is held fixed

volatility support
  = final verdict(11) != final verdict(10)
  # candidate execute is held fixed
```

Additional diagnostics record volatility regime-label changes between `(10)` and `(11)`, plus joint final-verdict changes between `(00)` and `(11)`.

This avoids a three-path attribution bug where the execute dimension could incorrectly receive zero support merely because it only becomes action-relevant after the volatility threshold also changes.

Only **final-verdict changes** count as causal support. A `NORMAL -> VOLATILE` relabel that leaves an already-`OBSERVE` route as `OBSERVE` is not evidence that the volatility threshold altered action.

## Frozen context

The following must remain uniform across the replay corpus:

- all engine-policy fields except `execute_net_edge`;
- all regime-policy fields except `volatile_return_bps`;
- full `RegimeExecutionPolicy`;
- rolling-window policy;
- baseline execute threshold;
- baseline volatility threshold.

Joint volatility calibration additionally requires the intended causal direction:

```text
NORMAL   -> ALLOW
VOLATILE -> OBSERVE_ONLY or REJECT
```

This prevents a numeric volatility tie-break from being interpreted as conservative under an inverted gate policy.

`JointPolicyContext` is recursively copied and frozen. Its inner SHA-256 is checked at construction and again when a joint holdout envelope is verified, so mutating raw context and merely recomputing the outer report digest cannot forge the measurement context.

## Candidate eligibility

A calibration candidate must satisfy all explicit evidence guardrails plus minimum causal-support counts. Causal support is an **eligibility gate**, not a score objective; more changed decisions are not automatically better.

The default selection order among eligible calibration candidates is:

```text
higher truth-rate lower bound
-> higher survival lower bound
-> more truth events
-> fewer indeterminate outcomes
-> lower overprediction penalty
-> higher execute threshold
-> lower volatility threshold
```

Validation never participates in this ordering.

## Holdout firewall

The candidate pair is frozen before validation is replayed. Validation may:

- pass the selected pair;
- fail performance guardrails;
- report insufficient truth support;
- report insufficient out-of-sample causal support.

Validation may **not** select a fallback pair.

## Evidence

The deterministic joint holdout report binds:

- source replay-bundle SHA-256;
- frozen policy context and baseline tuned values;
- chronological split membership and subset digests;
- full 2D candidate grid;
- baseline, execute-only, volatility-only and joint result digests;
- calibration metrics and per-dimension causal-support counts;
- selected candidate pair;
- untouched validation evaluation;
- selection semantics and validation firewall flags.

The report uses schema:

```text
resonance.arbitrage.joint-holdout-report/v0.1
```

## CLI

```bash
resonance-joint-holdout-calibration replay-bundle.json \
  --validation-fraction 0.30 \
  --execute-threshold-bps 25,30,35,40 \
  --volatile-threshold-bps 20,40,60,75 \
  --min-calibration-operations 20 \
  --min-validation-operations 10 \
  --min-calibration-truth-events 10 \
  --min-validation-truth-events 5 \
  --min-truth-lower-bound 0.60 \
  --min-survival-lower-bound 0.70 \
  --min-calibration-execute-causal-changes 1 \
  --min-calibration-volatility-causal-changes 1 \
  --min-validation-execute-causal-changes 1 \
  --min-validation-volatility-causal-changes 1
```

All numeric values are explicit caller-supplied paper-model guardrails, not trading recommendations.

## Safety boundary

v0.10 is offline and paper-only. It reads replay bundles and emits deterministic calibration evidence. It adds no account access, private exchange APIs, signing, order placement/cancel, wallet interaction, transfers, bridges, daemon, or live execution path.
