# v0.13 — Evidence-Bound Policy Promotion Gate

v0.13 adds a governance boundary between offline calibration/stability evidence and a policy becoming a canonical promotable **paper** policy.

```text
verified replay bundle
  -> verified v0.11 walk-forward report
  -> verified v0.12 stability decomposition
  -> calibration-selected policy support across folds
  -> promotion guardrails
  -> deterministic promotion decision
  -> SHA-256 promotion receipt
```

Promotion is not live execution. The layer performs no exchange authentication, order placement, signing, transfers, wallet actions or deployment.

## Why this layer exists

Before v0.13 the repository could answer:

- which candidate won a calibration fold;
- whether the frozen candidate passed untouched validation;
- whether the calibration process remained stable through time;
- which post-hoc drift drivers were associated with failed folds.

It did not yet define a separate, auditable statement of the form:

> this exact calibration-selected policy, under this exact frozen policy context and this exact evidence chain, is eligible to become the canonical paper policy.

That distinction matters because calibration score, validation success, temporal stability and policy promotion are different facts.

## Candidate-selection firewall

The promoted candidate is selected **only** from the candidates already chosen by calibration inside the walk-forward folds.

For each exact pair:

```text
(execute_net_edge_bps, volatile_return_bps)
```

v0.13 counts how many walk-forward calibration folds selected that pair. The unique highest-support pair becomes the calibration-consensus candidate.

Validation is not allowed to choose between candidates. It may only veto the already-determined calibration-consensus candidate.

Therefore this is forbidden:

```text
candidate A wins calibration consensus
candidate A fails validation veto
candidate B happened to validate better
=> promote B
```

The correct result is fail-closed: candidate A is blocked and no fallback candidate is selected.

## Promotion guardrails

`PolicyPromotionGuardrails` exposes explicit evidence requirements:

```text
min_selected_policy_folds
min_candidate_supporting_folds
min_consensus_fraction
min_candidate_validation_pass_rate
```

The defaults are evidence floors, not trading recommendations.

Promotion also requires:

- `WalkForwardStatus.PASSED_STABILITY`;
- `DecompositionStatus.STABLE_BASELINE`;
- a unique calibration-consensus candidate;
- enough selected-policy folds;
- enough direct support for the consensus candidate;
- consensus fraction at or above the configured floor;
- candidate validation pass rate at or above the configured veto floor.

## Explicit statuses

```text
PROMOTED
BLOCKED_WALK_FORWARD
BLOCKED_DECOMPOSITION
INSUFFICIENT_SELECTED_POLICIES
AMBIGUOUS_CALIBRATION_CONSENSUS
CONSENSUS_BELOW_FLOOR
INSUFFICIENT_CANDIDATE_SUPPORT
CANDIDATE_VALIDATION_BELOW_FLOOR
```

Ambiguous calibration consensus fails closed rather than using a hidden tie-breaker.

## Evidence

Schema:

```text
resonance.arbitrage.policy-promotion-report/v0.1
```

The canonical payload binds:

- replay bundle SHA-256;
- walk-forward report SHA-256;
- stability-decomposition report SHA-256;
- frozen joint policy-context SHA-256;
- promotion guardrails;
- every calibration-selected candidate and exact supporting fold indexes;
- which supporting folds later passed or failed validation;
- the final promotion decision and its exact candidate, if any;
- the invariant that candidate selection comes from calibration selections only;
- the invariant that validation can only veto;
- the invariant that decomposition never selects or mutates policy;
- explicit paper-only/advisory semantics.

The lightweight envelope verifier checks canonical structure, SHA-256 and decision/support consistency even if an attacker recomputes the outer digest after a semantic edit.

The full bundle-binding verifier reruns the complete evidence chain and requires the promotion report to reproduce byte-for-byte at canonical-payload level.

## Decomposition semantics

v0.12 remains post-hoc diagnostic evidence. Its drift drivers never select, mutate or rescue a policy.

v0.13 requires a decomposition report that is cryptographically and semantically bound to the same replay bundle and walk-forward report. A non-stable decomposition status blocks promotion, but diagnostic driver thresholds do not become a hidden policy-selection objective.

## CLI

`resonance-policy-promotion` recomputes walk-forward stability and stability decomposition from a local replay bundle, applies promotion guardrails and emits the deterministic promotion envelope.

Example:

```bash
resonance-policy-promotion replay-bundle.json \
  --execute-threshold-bps 25,30,35,40 \
  --volatile-threshold-bps 20,40,60,75 \
  --initial-calibration-operations 20 \
  --validation-operations 10 \
  --min-calibration-truth-events 10 \
  --min-validation-truth-events 5 \
  --min-truth-lower-bound 0.60 \
  --min-survival-lower-bound 0.70 \
  --regime-tv-threshold 0.25 \
  --route-tv-threshold 0.25 \
  --capacity-drop-fraction-threshold 0.25 \
  --quote-age-increase-ms-threshold 500 \
  --overprediction-increase-bps-threshold 10 \
  --causal-support-rate-drop-threshold 0.20 \
  --promotion-min-selected-policy-folds 3 \
  --promotion-min-candidate-supporting-folds 2 \
  --promotion-min-consensus-fraction 0.67 \
  --promotion-min-candidate-validation-pass-rate 0.67
```

All numeric thresholds are caller-supplied governance and diagnostic parameters. They are not represented as universal market constants or expected-return claims.

## Safety boundary

v0.13 remains offline/paper-only and adds no:

- private exchange API access;
- account credentials;
- order placement or cancellation;
- signing or wallet interaction;
- transfers, bridges or settlement actions;
- daemon or autonomous live execution;
- deployment of a promoted policy into a live trading system.
