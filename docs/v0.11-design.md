# v0.11 — Temporal Walk-Forward Stability

v0.11 tests whether the v0.10 joint policy remains credible across **multiple chronological out-of-sample windows**.

It remains offline and paper-only. It does not place orders, sign transactions, access private exchange endpoints, move funds, interact with wallets, or run a trading daemon.

## Why one holdout is not enough

A single calibration/validation split answers whether one frozen policy survived one future slice. v0.11 asks whether the calibration rule keeps producing policies that survive as time advances.

```text
captured replay corpus
  -> logical-operation ordering
  -> outcome-availability causal boundary
  -> expanding calibration prefix
  -> v0.10 joint calibration
  -> freeze selected pair
  -> next untouched validation slice
  -> record pass/fail + selected pair
  -> advance horizon
  -> repeat
  -> aggregate temporal stability
```

## Outcome-availability firewall

Splitting only by `detected_at_ms` is insufficient when calibration uses realized outcomes.

```text
operation A detected       t=100
operation B detected       t=200
A outcome becomes known    t=250
```

A validation decision at `t=200` must not be calibrated using A's outcome from `t=250`.

A walk-forward cut is therefore valid only when:

```text
max(calibration outcome observed_at_ms)
    < min(validation detected_at_ms)
```

Equality fails closed because ordering is ambiguous at the same timestamp. All attempts of one `logical_operation_id` remain together; operation availability is the maximum `outcome.observed_at_ms` across attempts.

## Expanding folds

The first fold uses the earliest causally valid boundary with at least the configured initial calibration population. Each later fold expands calibration by the previous validation slice.

```text
fold 1: calibration=A       validation=B
fold 2: calibration=A+B     validation=C
fold 3: calibration=A+B+C   validation=D
```

Validation windows do not overlap. A later fold may use outcomes from an earlier validation window only after those outcomes are available before the later validation window begins.

## Exact reuse of v0.10 semantics

Every fold invokes the existing v0.10 joint holdout engine. The fold forces exactly one split by setting its internal split geometry to the already planned calibration and validation counts. All other guardrails remain unchanged.

The v0.10 candidate search remains:

```text
execute_net_edge_bps × volatile_return_bps
```

and causal support remains the symmetric 2×2 counterfactual:

```text
(00) baseline
(10) candidate execute + baseline volatility
(01) baseline execute + candidate volatility
(11) joint candidate

execute support    = final(11) != final(01)
volatility support = final(11) != final(10)
```

Validation never selects a fallback.

## Fold evidence

Each fold binds:

- ordered calibration logical-operation IDs;
- ordered validation logical-operation IDs;
- calibration max detection timestamp;
- calibration max outcome-availability timestamp;
- validation min/max detection timestamps;
- validation max outcome-availability timestamp;
- fold replay-bundle SHA-256;
- the complete nested v0.10 joint holdout report envelope.

The outer verifier requires the nested report to use the same candidate grid, frozen policy context and non-split guardrails, plus the exact fold split and fold bundle digest. Only split geometry is allowed to vary with the expanding fold.

## Temporal metrics

v0.11 reports:

```text
total_folds
passed_folds
failed_folds
validation_pass_rate
selected_policy_folds
selected_policy_coverage
unique_selected_policies
policy_switches
policy_switch_rate
min/max selected execute_net_edge_bps
min/max selected volatile_return_bps
```

A failed or sparse v0.10 fold is counted as a failed fold. It is not silently removed from the denominator. Policy switching is measured across the chronological sequence of folds that produced a selected policy.

## Stability gate

`PASSED_STABILITY` requires:

```text
total_folds >= min_folds
selected_policy_folds >= min_selected_policy_folds
validation_pass_rate >= min_validation_pass_rate
policy_switch_rate <= max_policy_switch_rate
```

Otherwise the report is explicit: `INSUFFICIENT_CORPUS`, `INSUFFICIENT_FOLDS`, or `UNSTABLE`.

The thresholds are caller-supplied research guardrails, not trading recommendations.

## Deterministic evidence

Schema:

```text
resonance.arbitrage.walk-forward-report/v0.1
```

The report binds the source replay-bundle SHA-256, ordered source operation list, frozen v0.10 context, walk-forward policy, joint candidate grid, deterministic fold plan, unused corpus tail, every nested v0.10 report envelope, aggregate metrics and final status.

`verify_walk_forward_report_envelope()` validates outer integrity, outcome-availability boundaries, expanding-prefix geometry, nested v0.10 envelopes, fold guardrail consistency, and recomputes aggregate metrics from nested fold evidence.

`verify_walk_forward_report_bundle_binding()` reruns the complete process against the original typed `ReplayBundle` and requires exact canonical reproduction.

## CLI

```bash
resonance-walk-forward-stability replay-bundle.json \
  --execute-threshold-bps 25,30,35,40 \
  --volatile-threshold-bps 20,40,60,75 \
  --initial-calibration-operations 30 \
  --validation-operations 10 \
  --min-folds 3 \
  --min-selected-policy-folds 2 \
  --min-validation-pass-rate 0.67 \
  --max-policy-switch-rate 0.50 \
  --min-calibration-truth-events 10 \
  --min-validation-truth-events 5 \
  --min-truth-lower-bound 0.60 \
  --min-survival-lower-bound 0.70 \
  --min-calibration-execute-causal-changes 1 \
  --min-calibration-volatility-causal-changes 1 \
  --min-validation-execute-causal-changes 1 \
  --min-validation-volatility-causal-changes 1
```

The CLI reads a local replay-bundle envelope and emits deterministic JSON. It performs no network requests.

## Safety boundary

v0.11 is a calibration/stability laboratory only. It adds no private API credentials, account endpoints, order placement/cancellation, transaction signing, wallet operations, transfers/bridges, automatic capital allocation, background trading process, or live execution path.
